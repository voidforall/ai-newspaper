# AI Newspaper × Horizon：面向 release 的产品与架构建议

调研日期：2026-10-20。结论分为「已核实」「判断」「建议」；后两者不代表已实现能力或已验证的用户需求。Horizon 代码证据另见 [原始调研](horizon-primary-research.md)。本项目本地基线为 `613a90c`；线上部署与本地不同，不能混为同一版本。

## 结论与建议定位

建议切入 **面向 AI 应用开发者、每天五分钟读完的可核查技术报纸**：今天发生了什么、相对前次有什么实质变化、对构建产品有什么影响、哪些结论仍只是厂商主张。五分钟是内容预算目标，需要实际读者验证。

Horizon 已在「个人信息雷达」上覆盖多源、个性化处理、历史背景、推送及社区源生态。我们的机会是把**事件级编辑、证据透明、连续追踪和可传播的成品报纸**做成一体体验。报纸排版本身很容易复制；只有持续的编辑质量、可积累的事件与更正记录、读者习惯可能逐渐形成优势。当前没有证据证明我们已拥有这些壁垒。

不要同时追求面向所有人的聚合器、完整 newsletter SaaS、agent 平台和新闻网站。首发优先服务读者；开源引擎与 recipe 是复用和贡献入口。需要验证的商业分叉是：用户想直接读，还是主要想自己搭建。

## 1. 真实现状：线上能跑，距离可发布产品仍有落差

### 我们已经拥有的基础

- 本地代码有 HN、RSS/Atom、GitHub Releases、受域名与调用预算限制的 agent research；recipe 可以组合来源，builder 可以导出自定义 JSON。证据：[source-adapters.js](../../src/source-adapters.js)、[edition-recipes.json](../../edition-recipes.json)、[recipe-builder.js](../../src/recipe-builder.js)、[agent-research.js](../../src/agent-research.js)。因此不能把「多源」「配置式订阅」当作从零开发的功能。
- 选稿后才抓正文和编辑，issue JSON 与静态渲染分离，已有两个模板和分期归档。保留这条简单路径。证据：[cli.js](../../src/cli.js)、[render-issue.js](../../src/render-issue.js)。
- 本地 `npm test` 27/27 通过，`npm run build` 成功。这证明现有检查通过，不证明内容正确或线上已发布这些能力。
- 浏览器实查 [线上首页](https://voidforall.github.io/ai-newspaper/)：仅 HN 栏目，95 期，最新显示 2026-10-19。最近五次 Actions 运行成功。持续生成是可靠性基础，但不能等同于持续有人阅读。

### 首发前必须面对的问题

1. **当前线上实际在发布降级内容。** [2026-10-19 期](https://voidforall.github.io/ai-newspaper/editions/2026-10-19-hacker-news/)出现广告/网站导航进入正文、占位摘要、HN 点数充当影响说明。对应 [Actions 运行](https://github.com/voidforall/ai-newspaper/actions/runs/39268863110) 的生成步骤里 `OPENAI_API_KEY`、`OPENAI_MODEL` 均为空。只能据此认定该次运行没拿到配置，不能推断账户全局没有任何密钥。AI 日报的价值在这条运行路径上没有兑现。
2. **本地与线上版本分叉。** 本地有新 recipe、builder、validator，线上仍是旧首页与固定刊名。release 要先对齐远端、保存已有 95 期归档、确认部署提交，再决定如何集成；不能直接用本地六期历史覆盖线上档案。调研没有执行 pull、merge、push 或部署。
3. **链接可追溯不等于事实已核实。** 本地 validator 检查长度、分类与链接格式，没有校验摘要中的断言是否得到正文支持。[validate-issue.js](../../src/validate-issue.js)。
4. **原文抓取过于脆弱。** 目前正则提取 HTML，再取正文前部；编辑输入最多 4,000 字符，容易保留页面杂讯、丢掉后文限定条件。[investigate-content.js](../../src/investigate-content.js)、[edit-issue.js](../../src/edit-issue.js)。应先用已知失败的真实页面做提取对照，再选成熟正文提取实现；arXiv、GitHub 等结构化源优先读专用摘要/README，勿把站点外壳当文章。
5. **多源排序和去重有结构性缺口。** 无 AI 时直接比较 HN points 与 RSS/GitHub 的位置分数；选稿完成后才精确 URL 去重，重复候选会先占名额，且不会合并多个出处。需要统一编辑标准并把去重移到选稿前。[edit-issue.js](../../src/edit-issue.js)、[create-issue.js](../../src/create-issue.js)、[rss.js](../../src/rss.js)、[github-releases.js](../../src/github-releases.js)。
6. **发现与传播入口不足。** GitHub About 描述为空，当前仓库根目录未见 LICENSE；网页缺少独立新闻页、分享元数据、RSS 和明确阅读/订阅入口。README 的生成路径描述与当前代码也有偏差。开源首发要先明确许可与真正可执行的 quickstart。[本地 README](../../README.md)、[仓库](https://github.com/voidforall/ai-newspaper)。

## 2. 从 Horizon 学什么

Horizon 的基本能力与入口见 [仓库说明](https://github.com/Thysrael/Horizon)。本次页面显示约 10.8k stars、1.6k forks；是关注度快照，不是活跃用户数。它的 README 仍将 GitHub Releases、PyPI 发布列为待办，说明获得关注并不依赖先把包发布体系做全。

| 可借鉴的机制 | 对我们解决什么问题 | 采用方式与时机 |
| --- | --- | --- |
| Profile：内容类型决定评分标准与输出块 | 论文、版本更新、产业新闻不该套同一段 prompt | v0.1 在 recipe 引用轻量 editorial policy：受众、评分维度、来源/栏目配额、字数；论文输出限制条件，release 输出兼容影响；不先做插件系统 |
| 先分析、过滤、去重，再做昂贵 enrichment | 重复或低价值候选浪费抓取与模型预算 | 先统一 URL 和合并出处，再按编辑标准选事件；只有入选事件抓取/补证据；延续我们已有「先选再抓」优势 |
| Digest 总量与分类配额 | HN 或高频 AI 主题淹没其他真正有用变化 | 目标 5–8 个事件，以信息价值为准，不为凑数发布；设置每来源/主题上限，配额是上限不是填满要求 |
| 成熟正文提取、结构化 enrichment、讨论摘要 | 摘要被导航污染、原文与评论混在一起 | 把来源事实、厂商主张、社区观点分开记录；讨论仅在有实质增量时加入，并保留出处 |
| 分阶段运行产物与历史检索 | 失败后难排查、重跑重复花费、事件背景断裂 | 先复用 `research/` 与 issue JSON，存运行摘要和输入 hash；只有具体重试需求才扩展 checkpoint/cache；历史先用关键词索引 |
| Wizard、可直接看的 demo、配置示例 | 新人不知道输出长什么样、如何开始 | 首屏直接读一份成品；fork/配置/生成的教程实测；已有 builder 打磨为可复用 preset 入口 |
| 社区来源贡献、公开日报、跨渠道展示 | 产品价值难以解释，贡献不知从何入手 | 让用户贡献带样例成品的 recipe/专题 desk；先仓库 PR 审核，不建 marketplace |

源码和对应边界详见 [Horizon 原始证据报告](horizon-primary-research.md)。MIT 允许借鉴或复用，但实际复制代码必须保留对应版权与许可通知；优先移植机制和测试用例，避免为借功能重写成 Python。

### 暂缓追随的范围

X/Telegram 全采集、微信登录与 IMAP 订阅管理、全套模型供应商、MCP server、开放贡献市场不作为首发门槛。它们没有直接解决眼下读者获得的内容质量。先开放一个经过真实运行验证的模型路径；如果目标用户明确卡在兼容端点，再加 provider 接口。推送从静态 RSS 开始，邮件先验证需求再选择现成服务。

## 3. 什么能成为自己的 edge

**不是独特卖点的能力：** AI 摘要、why-it-matters、多源、双语、历史背景、个性化 prompt、GitHub Pages。Horizon 已有或有明确实现。尤其它 [2026-10-20 的日报](https://thysrael.github.io/Horizon/2026/10/20/summary-zh.html)已引用以前的日报做背景；「加记忆」本身不构成差异化。

### A. 可核查的编辑成品：首发主张

每个事件回答四个固定问题：事实是什么；证据来自哪；对 AI 应用开发者有什么影响；哪些仍未证实。将关键断言关联来源摘录/段落，不只在文末挂一个链接。区分「官方声称」「独立验证」「社区体验」以及「资料不足」。不要显示模型自报的 93% 置信度来假装已验证。

Horizon 样本也提醒我们注意跨块一致性：同一条 Timestral 的摘要说缺少规模/访问方式，后续背景却给出规模和代码入口。这是单期样本观察，不能据此推断其整体错误率。我们的验收应包含摘要与背景的一致性；一个模型再审一次也不应被包装成独立核实。

读者收益：不用逐条打开十篇报道确认有没有夸大。积累优势：人工抽查过的证据与更正记录、优质样例与稳定编辑标准。UI 可以被复制，持续质量记录更难复制。

### B. 事件连续追踪：首发做小，后续积累

用稳定 `eventId` 汇合官方发布、代码、论文、社区讨论。新一天重点写「新增了什么、原判断是否改变」，没有变化不重复上版。事件页列时间线、证据及更正，而不仅是按日期找历史日报。

它与 Horizon 的历史背景检索有重叠；差别需要落实为明确事件身份、结构化变化和更正流程，并通过用户验证其价值，不能预先声称技术领先。

首发只选少数重点事件手工确认聚类。关键词/实体/URL 规则足够时不用向量数据库；若误合并率暴露问题，再做候选匹配与人工确认。没有证据的「新变化」不生成。

### C. 报纸成为传播载体：获客切入口

首页直接呈现当天有限的一期，先读后配置；保留五分钟主版，证据和深读折叠。新闻有永久链接，整期有封面与 OG 图；手机上单栏可读，桌面报纸保留辨识度。分享图片带标题、日期、网址和出处提示，点击回到可核查网页。

报纸美学是获客钩子，不是长期壁垒。独特组合是「有限的阅读预算 + 明确的编辑判断 + 可核查证据 + 连续事件档案」。先实现 print CSS，PDF 等到确实有人要求导出，避免为海报先造完整排版引擎。

### D. 可复用的专题 desk：贡献切入口

每个 recipe 不只是一组 RSS，而是来源、编辑标准、样例期刊、适用受众的完整小出版物。先维护 AI Builder 一个主 desk，另给一个能证明可扩展性的样例；不要把首页塞满低质量空栏目。接受高质量 PR 后再形成贡献目录。Horizon 同样有 profile 和社区源，recipe 生态也不是天然独占，必须靠成品质量获得差别。

## 4. 建议架构：让每一步对最终报纸负责

保持 Node.js、离线生成和静态 Pages。JSON 仍是持久接口；先给数据 schema 加版本，确保旧档案仍能渲染。

```text
Source adapters → Article candidates
  → URL 规范化 / 合并出处 / 事件候选分组
  → Editorial policy 筛选 + 栏目/阅读预算
  → 入选事件正文提取 / 定向补证据
  → Evidence records → Editorial draft
  → 硬性完整性检查 + 人工抽查/审核状态
  → Published issue JSON
  → 报纸 / 事件页 / RSS / 分享封面
```

最小数据边界建议：

- `Article`：原始 URL、canonical URL、来源、来源发布时间、抓取时间、提取状态。不能把查询日期当作来源真实发布时间；当前 agent research 有这种混淆风险。
- `Evidence`：来源 URL、短摘录/定位、抓取时间、支持或限制的断言 ID。完整原文如为排查临时缓存，不公开打包进网页/Git；不把抓取材料当成可信指令。
- `Event`：稳定 ID、多个 article/evidence ID、前次报道、这次新增事实。首发人工合并可接受。
- `Issue`：schemaVersion、recipe/policy 版本、event 引用及当期快照、AI/人工/降级编辑状态、draft/published、修订与更正记录。已发布期刊不能因后来事件编辑而悄悄改写。
- `Run summary`：来源成功/失败、候选/入选/去重数、正文可用数、模型和 prompt 版本、耗时及 API 实际 usage；不要编造成本估算或存密钥。全链路不要求 token 级 trace。

故障策略：某个非关键源失败时记录缺口并继续；关键源缺失则保留上一期并提示未更新。AI 失败时保存明确标记的链接草稿，不把原文前两句当审核后的 AI 成品。抓取失败可尝试可信 feed 摘要，否则跳过/留待审；不能靠占位文案填满版面。每阶段给网络请求超时和有界重试；只有实际遇到重复成本后再增加缓存。

发布约束：完整性硬检查负责阻止无来源、无正文依据、重复事件、占位摘要；内容真伪仍依赖证据抽查与编辑判断。不要让自动校验宣称能证明事实正确。所有输出从同一个已发布 issue 生成，避免网页与邮件内容分叉。

## 5. Release 路线与验收（顺序建议，不是工期承诺）

### 第一阶段：真实可交付的 release candidate

1. 对齐线上和本地，保留历史档案；确认目标提交、生成配置和公开演示。复查运行里空的 AI 配置并完成一次实际 AI 生成，记录成本与耗时。
2. 用线上已暴露问题的原始页面做端到端质量样本，改善提取，统一跨源选稿标准，把去重移到选稿前。处理失败后输出明确草稿/状态。
3. 一个 AI Builder desk、5–8 个事件、中文主版；英文版等确有使用需求再同步。正文只写有证据支持的内容；事件至少一个可定位的一手来源或明确标注无法核实。
4. 首页直接读当天，提供原文/证据入口、新闻永久链接、移动端布局、RSS、OG 分享和 GitHub 入口。提供质量较好的固定 demo，不让新人先填表才知道产品价值。
5. 更新 README：成品截图、定位、在线地址、零 key 样例 build、真实生成所需配置、可测量的运行数据、fork 部署路径；补充许可、changelog 和明确的支持边界。

**建议验收：** 新手在干净环境能按说明构建样例并完成一次真生成；连续七期人工抽查没有发布占位/导航垃圾；关键断言有来源、待核实项显式标记；重试不覆盖已发布档案；手机阅读/键盘访问/长标题不出框。七期只证明短期质量，不证明全年可靠。

### 第二阶段：让读者回来

加入少量重点事件的 timeline/delta 与更正记录，邀请 10–20 名实际 AI 开发者试读。记录他们在一周内是否回来、是否打开证据、是否觉得一条信息改变了技术判断。先用访谈与自愿反馈验证；不为测量引入账号系统。以「至少 5 位愿意持续订阅、能说出具体价值」作为探索阶段建议门槛，不把它当行业基准。

### 第三阶段：公开发布与增长实验

- 用三份高质量样例和一段 30–45 秒「打开 → 五分钟版 → 证据 → 事件变化 → 分享」演示建立理解；不是只贴架构图。
- 一句话文案建议：**“A five-minute newspaper for AI builders. Every story shows its sources, what changed, and why you should care.”** 中文：“给 AI 开发者的五分钟报纸：看清新变化，查得到依据。”只有相应能力上线后再使用完整承诺。
- 读者线：公开样例 → 单条/整期分享 → 回到当天 → RSS/后续邮件 → 留存。维护者线：看样例 → fork recipe → 发第一期 → 贡献 desk。两个入口分别写清楚。
- 在开发者活跃的中文社区和英文 HN/Reddit 做适合各自读者的发布；投递 HelloGitHub 等项目推荐渠道。先获取具体反馈再扩散；这里是渠道实验建议，未核实当前各渠道发帖规则，发布前应确认。没有在本次调研中发送帖子或联系任何人。
- 发布复盘看读者回访、订阅意愿、分享带回阅读、fork 后真实生成成功；stars 作为曝光指标，不作为质量或留存证明。
- 后续考虑周刊/专题和贡献 recipe 的传播价值；不一开始建立社区服务和订阅后端。

Horizon README 致谢 LINUX.DO、HelloGitHub 和小红书推广，并展示 demo、截图、多语文档与贡献入口。这支持「成品展示 + 社区分发值得学习」的判断，但没有渠道归因数据，不能声称某个渠道造成了它的 star 增长。

## 6. 最值得先实现的三件事

1. **把一次真实生成变成值得公开阅读的一期。** 修复配置/提取/降级内容，录入编辑状态与来源证据；这是其余工作的前提。
2. **让首次访问直接读懂价值。** 一个主 desk、有限新闻、好读手机版、单条永久链接和分享封面；再补 README/demo/release 包装。
3. **用重点事件积累连续性。** 小规模人工确认 eventId，展示新增事实、证据和更正，用实际读者验证是否值得回来。

本次只做调研与报告，没有修改产品代码、发布 release、合并远端或配置密钥。
